# CLAUDE.md — Masar

Masar is a full-stack TypeScript framework: **one clear path from idea to production**.
Apps are made of modules; each module owns its schema, actions, pages, routes and jobs.
This repo contains the framework packages plus a playground app used to develop and test them.

## Working with Ziad (the owner)

- Talk to him in **Egyptian Arabic**, direct and friendly; keep technical terms in English.
- He builds the framework with you: explain *why* for design decisions, propose one clear
  recommendation instead of a list, and push back when an idea hurts simplicity or stability.
- Before a large change (new package, new public API, breaking change), describe the plan in a few
  lines and wait for his OK. Small fixes and internal refactors: just do them and report.
- Be explicit about what you verified (typecheck / ran it / tested in the browser) and what you didn't.

## How an app works (keep these mental models intact)

- **Module** = `src/modules/<name>/`: `module.ts` (defineModule: name must equal folder, prefix, store,
  expose {ui, api}, depends), `schema.ts` (models), `actions.ts`, `routes.ts` (optional, paths relative
  to the module prefix), `jobs/`, `views/pages/` (file = URL: `index.tsx`, `[id].tsx`), `views/components/`.
- **Discovery is by `import.meta.glob`** in the generated `.masar/server.ts`; no registration files.
- **Actions** are the only place for business logic. Same import works on the server (direct call)
  and in the browser (plugin swaps the module for `__masarAction` RPC calls to
  `POST /_masar/actions/<module>/<name>` with header `x-masar-action`). `expose.api` adds
  `GET|POST /api/<module>/<kebab-name>`.
- **Pages**: default export = React component; optional `export async function load(ctx)` runs on the
  server and its return value becomes props (`PageProps<typeof load>`). The plugin blanks `load`/`route`
  in the client build (whitespace, positions preserved) so imports used only by load get elided.
- **Routing order**: pages and custom routes are registered together, most specific first
  (static before dynamic). Duplicate method+path throws at boot.
- **Data layer**: `db(model)` → typed `Table`. Every model has `id` (UUIDv7 string), `createdAt`,
  `updatedAt` (ISO strings). Same API for SQLite (`node:sqlite`), Postgres (postgres.js) and MongoDB.
  Each module picks a connection with `store`. No cross-store joins or transactions.
- **Relations** (`with()` in `src/db/query.ts`): no relation declarations; `f.ref('table')` carries the
  table as a type param (Field's 4th generic) and `model()` keeps the table literal, so `with({ key: Model |
  Query | [either, 'field'] })` types one-vs-many. Loading is one IN query per relation, chunked by 1000.
- **Transactions** (`src/db/transaction.ts`): `transaction(fn, { store? })` puts a tx adapter in
  AsyncLocalStorage; `getAdapter()` returns it for that connection and throws for others. Nested calls
  join. SQLite shares one handle, so its executor makes other queries wait while a tx is open.
- **Schema sync**: `masar dev` and `masar db:sync` create tables/collections, add columns and indexes.
  They never drop or rename; that is what migrations are for.
- **Migrations** (`src/db/migrations.ts`, globbed from `modules/*/migrations/*.ts`): forward-only,
  `<YYYYMMDD>_<HHMMSS>_<name>.ts`, ordered by timestamp across modules, run on the module's store.
  History in `masar_migrations`, lock row in `masar_locks` (both created on demand, not kernel models).
  `masar migrate` = migrations then sync. Dev never auto-runs them (a half-saved file would be recorded as done).
- **i18n + theme** (`src/i18n/`, `src/react/i18n.ts`, `packages/cli/src/i18n.ts`): `defineApp({ locales })`,
  locale per request from cookie `masar_locale` → Accept-Language → default; dir derived (no `dir` option).
  Messages = `src/locales/<code>.json` globbed into the server entry and shared as `masar.i18n` (current
  locale only). The CLI scanner adds `t('literal')` keys (not in comment lines) plus module titles; dynamic
  keys like `t(variable)` are not found, so write literals. Theme cookie `masar_theme`; the root view sets
  `class="dark"` or an inline system-preference script. UI components live in the template, logic in core.
- **Storage** (`src/storage/`, `src/config/storage.ts`): disks local | s3 (SigV4 presigning written by hand,
  every S3 call is a presigned fetch). `f.file()`/`f.files()` are json fields with `meta.file` rules. Uploads:
  `POST /_masar/uploads/prepare` (signed in; checks the field's rules) → browser PUTs to S3 or to
  `PUT /_masar/uploads` (signed, streamed, size-capped). StoredFile carries an HMAC `sig` (APP_KEY; a dev key
  derived from cwd in development); `checkValue` rejects unsigned refs. Table.update/delete remove orphaned
  files. Local reads: public disk url prefix or `/_masar/files` signed links, Range support, sandbox CSP,
  not rate limited. `masar start` refuses to boot without APP_KEY.
- **Admin** (`src/admin/`): kernel builds it when `src/modules/admin` exists (module authorize defaults to
  role('admin')). Server: `server.ts` turns models (+ `resources/*.ts`, `dashboard.ts` globbed in the
  server entry) into metadata shared as `masar.admin` on admin pages, and answers `POST /_masar/admin/:op`
  (list, record, options, save, delete, run, export, dashboard). UI: `@masar/core/admin` (React, Tailwind
  classes with the app's tokens; the app CSS has `@source` pointing at core/src/admin). Module layouts:
  `views/layout.tsx` replaces AppLayout for that module. Icons: the Vite plugin serves
  `virtual:masar/icons` with only the Lucide names found in src (`icon: '...'`, `<Icon name>`) plus the
  admin's own list in `cli/src/icons.ts` — add new built-in icon names there. Never use lucide's DynamicIcon:
  it makes Vite fetch all 1500 icons.
- **Errors in dev**: `@masar/core/dev-overlay` replaces Vite's overlay (`hmr.overlay: false` in cli/src/vite.ts).
  It loads from its own inline script in the root view (so it works when the app graph fails), shows
  build errors (`vite:error`), uncaught errors and rejections in the brand, with a "Next step" from Masar
  `→` lines or the HINTS table in dev-overlay.ts — add a row there for any confusing error you meet.
  ErrorPage.tsx (404/500) and the CLI boot error page share the same look. Try them all at /errors in the
  playground (broken files live in playground/error-test/, outside tsconfig on purpose).
- Module layouts (`views/layout.tsx`) load lazily with their module's pages; keep them out of eager globs
  or the admin UI ships to every visitor.
- Modules also take `authorize` (pages, routes and actions of the module) and `nav: false`.
- **Auth** (`src/auth/index.ts`): built-in `users`/`sessions` models (module "masar", default connection),
  scrypt passwords, sha256-hashed session tokens. Every action needs `authorize` ('public' | 'user' |
  rule like `role('admin')`): missing → boot error. Checked only when a request exists. Cookie for
  pages/actions, bearer only on `/api/*`. 401 on an HTML GET redirects to `auth.loginPath` if a page answers it.
  The `auth` module (login/register pages, login/register/logout/token actions) lives in the create-masar template.
- **Security** (`src/server/security.ts`, config `defineApp({ security })`): secure headers always on,
  in-memory rate limit per IP (default 300/60s, `false` to disable), CORS only on `/api/*` and only when
  `security.cors.origins` is set. The CLI servers pass `{ ip }` as the fetch env; `trustProxy` reads X-Forwarded-For.
- **Errors**: throw `MasarError(message, { hint, status })`. The hint is shown in the terminal and the
  dev error page. Every new error a developer can hit should have a hint that says what to do.

## Commands

```bash
pnpm install
pnpm dev                     # playground dev server, http://localhost:3000
pnpm typecheck               # tsc for core + cli
cd playground && npx tsc --noEmit -p .   # typecheck the app (also checks core types as consumed)
pnpm e2e                     # browser smoke test (needs pnpm dev running; first time: npx playwright install chromium)
cd playground && npx masar routes | npx masar db:sync | npx masar make:module <name> [--api] [--no-ui] [--no-crud]
pnpm build && pnpm start     # production build + server (the playground start script sets a dev APP_KEY); BASE_URL=... pnpm e2e works against it
node packages/create-masar/index.js ../some-app --local --db sqlite   # new app linked to this repo
```

## Definition of done for a change

1. `pnpm typecheck` and the playground `tsc --noEmit` pass.
2. If runtime behavior changed: restart `pnpm dev` (see gotcha 1) and run `pnpm e2e`.
3. If build/production paths changed: `pnpm build`, `pnpm start`, then `BASE_URL=... pnpm e2e`,
   and confirm no server code in `playground/dist/client/assets` (grep for `node:sqlite`, `findOrFail`).
4. If the generator changed: delete and regenerate a module in the playground and typecheck it.
5. If the template changed: generate a fresh app with create-masar `--local` and run it.
6. Update README.md / this file when a public API, command or convention changes.

## Hard-won gotchas (do not regress these)

1. **Changes in `packages/core` or `packages/cli` need a dev-server restart.** Vite only watches the
   app root, so edits to linked packages are not hot-reloaded.
2. **Vite's dependency scanner** calls `resolveId` with `options.scan === true` before our transforms
   run. Guards in the plugin must skip scan mode or startup breaks.
3. **postgres.js serializes jsonb itself.** Never `JSON.stringify` JSON values for Postgres
   (the `::jsonb` cast in placeholders is what tells it the type). SQLite does need stringify.
4. **Database drivers are loaded with `importDriver()`** (variable specifier): apps that don't use
   Postgres/Mongo must not need their packages or types. Keep driver types as local interfaces.
5. **Packages ship TypeScript source.** Vite compiles them (`ssr.noExternal: /^@masar\//`), the CLI runs
   through tsx. Production SSR build bundles everything except `postgres` and `mongodb`.
6. **React must stay single-instance**: `resolve.dedupe` covers react, react-dom, @inertiajs/react,
   so apps must list those three as their own dependencies.
7. **Hono's `onError` only receives `Error` instances**, so control-flow signals (`RedirectSignal`)
   extend Error.
8. **Do not add `verbatimModuleSyntax` to app tsconfig**: unused-import elision is what removes
   server imports from pages after `load` is stripped.
9. Singularizing module names in the generator is heuristic (`courses → course`, `classes → class`).
10. The tools that sync files to Ziad's machine cannot write `.env`; apps run on defaults and
    `.env.example` has the same content.

## Conventions

- TypeScript strict, ESM, 2-space indent, single quotes, no semicolons, trailing commas.
- Public API names: `defineX` for declarations, plain verbs for runtime (`db`, `action`, `dispatch`).
- One way to do each thing. Before adding an option, ask whether a convention can replace it.
- Generators must produce code that runs and typechecks with no edits.
- Comments explain *why*, not what. User-facing copy: sentence case, active voice, specific.
- No new dependencies without a clear reason; prefer what Vite, Hono, zod and the platform already give.
